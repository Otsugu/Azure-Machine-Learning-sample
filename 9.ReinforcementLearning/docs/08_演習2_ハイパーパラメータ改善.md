## 8.1 主要なハイパーパラメータの意味

| 引数 | 意味 | 大きくすると | 小さくすると |
|---|---|---|---|
| `--learning-rate` | 1 回の更新でどれだけ動くか | 速く学ぶが**不安定・発散しやすい** | 安定だが**遅い** |
| `--gamma` | **割引率**（どこまで先を見るか） | 長期的な計画ができる。**不安定になりやすい** | 安定。**長い手順のタスクが解けない** |
| `--batch-size` | 1 回の更新に使うサンプル数 | 勾配が安定。**1 更新が重い** | 速いがノイズが多い |
| `--buffer-size` | リプレイバッファの容量 | 古い経験も使える。**メモリを食う** | 新しい経験に偏る |
| `--learning-starts` | 学習開始までに集めるステップ数 | 初期の暴走を防ぐ | 早く学習を始める |
| `--n-sampled-goal` | HER が 1 経験から作る仮想経験の数 | 成功サンプルが増える。**計算が重い** | 効果が薄い |
| `--goal-selection-strategy` | HER のゴール選択方式（`future`/`final`/`episode`） | — | — |

> **$\gamma$ の目安**: 実効地平線 $\approx \frac{1}{1-\gamma}$（[01 章](01_強化学習の基礎.md) 1.2）。
> **1 エピソードは 50 ステップ**なので、$\gamma = 0.9$（実効 10 ステップ）ではエピソード全体を見通せません。

## 8.2 Sweep Job とは

Azure ML の **Sweep Job** は、**探索空間・サンプリング方式・早期終了ポリシー・目的関数**を指定すると、
**複数の学習ジョブ（trial）を自動で並列実行**してくれる機能です。

> **出典: Microsoft Learn** — [Hyperparameter tuning a model (v2)](https://learn.microsoft.com/azure/machine-learning/how-to-tune-hyperparameters?view=azureml-api-2)

### 構成要素

| 要素 | 説明 | 本ハンズオンでの指定 |
|---|---|---|
| **探索空間** | 各パラメーターの候補 | `Choice` / `Uniform` / `LogUniform` など |
| **サンプリング** | `grid` / `random` / `bayesian` | 演習では `grid` と `random` |
| **目的関数** | `primary_metric` と `goal` | **`final_success_rate` を `Maximize`** |
| **上限** | `max_total_trials` / `max_concurrent_trials` | **時間とクォータで決める** |
| **早期終了** | `BanditPolicy` など | **RL では要注意（8.4）** |

> **重要**: **`primary_metric` は、学習スクリプトが `mlflow.log_metric` で記録する名前と完全に一致**していなければなりません。
> 本テキストがメトリック名に `/` を使わず `final_success_rate` のように平坦にしているのは**このため**です。

### サンプリング方式の選び方

| 方式 | 向いている場面 | 注意 |
|---|---|---|
| `grid` | **候補が離散で少数**。全組み合わせを試したい | 組み合わせ爆発に注意 |
| `random` | 連続値を広く探索したい | — |
| `bayesian` | 予算があり効率よく探索したい | **「調整するハイパラ数 × 20 以上の試行」が推奨**（Learn 記載）。`choice` / `uniform` / `quniform` のみ対応 |

> **出典: Microsoft Learn** — [Sampling the hyperparameter space](https://learn.microsoft.com/azure/machine-learning/how-to-tune-hyperparameters?view=azureml-api-2#sampling-the-hyperparameter-space)

## 8.3 【強化学習に固有】乱数シードを探索空間に入れる

> **これが本章で最も重要な使い方です。**

強化学習は**同じ設定でも結果が大きくばらつきます**（[01 章](01_強化学習の基礎.md) 1.8）。
そのため **1 本の Run で「改善した」と判断してはいけません。**

Sweep Job の探索空間に **`seed` を入れる**と、**「同一設定 × 複数シードの反復実行」を 1 本のジョブで回せます。**

```python
sweep = job(
    seed=Choice(values=[0, 1, 2]),                 # ← 再現性の評価
    learning_rate=Choice(values=[1e-4, 3e-4, 1e-3]),
).sweep(
    compute="cpu-cluster",
    sampling_algorithm="grid",
    primary_metric="final_success_rate",
    goal="Maximize",
    max_total_trials=9,
    max_concurrent_trials=3,
)
```

これで **3 学習率 × 3 シード = 9 trial** が実行されます。

> **重要な読み方**
> - **同じ学習率の 3 シード間のばらつき**が「その設定の再現性」
> - **学習率間の差がシード間のばらつきより大きい**ときに初めて「学習率が効いた」と言える
>
> **この比較を必ず行ってください。** これをやらないと、単なる乱数の揺れを「改善」と誤認します。

## 8.4 【重要な注意】早期終了ポリシーと強化学習

Azure ML には、成績の悪い trial を途中で打ち切る**早期終了ポリシー**があります。

| ポリシー | 動作 |
|---|---|
| `BanditPolicy` | 主指標が最良値から一定割合（`slack_factor`）外れたら打ち切る |
| `MedianStoppingPolicy` | 中央値より悪ければ打ち切る |
| `TruncationSelectionPolicy` | 下位 X% を打ち切る |

> **出典: Microsoft Learn** — [Specify early termination policy](https://learn.microsoft.com/azure/machine-learning/how-to-tune-hyperparameters?view=azureml-api-2#early-termination)

> ⚠⚠ **強化学習では早期終了に注意してください。**
> **強化学習は「長い平坦期のあとに急に立ち上がる」ことが珍しくありません。**
> 早期終了を素直に使うと、**あとで伸びるはずの設定を序盤で切ってしまいます。**
>
> **対策**: `delay_evaluation`（評価開始を遅らせる）を必ず設定してください。
>
> ```python
> from azure.ai.ml.sweep import BanditPolicy
> early_termination = BanditPolicy(
>     slack_factor=0.2,
>     evaluation_interval=1,
>     delay_evaluation=5,   # ← 最初の 5 回の評価は打ち切り判定をしない
> )
> ```
>
> **本ハンズオンの演習では、学習時間が短いため早期終了は既定で使いません。**
> 使う場合の注意点として理解しておいてください。

## 8.5 コストの上限を決める

> ⚠ **Sweep は簡単に大量の計算資源を消費します。** 先に上限を決めてください。

| 設定 | 役割 |
|---|---|
| `max_total_trials` | **総試行数の上限** |
| `max_concurrent_trials` | **同時実行数**（クォータと `max_instances` を超えないこと） |
| `timeout` | **Sweep 全体の時間上限**（秒） |
| `trial_timeout` | 1 trial あたりの時間上限（秒） |

> **出典: Microsoft Learn** — [Command クラスの `sweep()` メソッド](https://learn.microsoft.com/python/api/azure-ai-ml/azure.ai.ml.entities.command?view=azure-python)
> `sweep()` のキーワード引数として `primary_metric`（必須）、`goal`（必須）、`sampling_algorithm`、`compute`、
> `max_concurrent_trials`、`max_total_trials`、**`timeout`**、**`trial_timeout`**、`early_termination_policy`、`search_space` が定義されています。

> **出典: Microsoft Learn** — [Manage and optimize Azure Machine Learning costs](https://learn.microsoft.com/azure/machine-learning/how-to-manage-optimize-cost?view=azureml-api-2)
> ジョブの `limits.timeout` で最大実行時間を制御できること、早期終了ポリシーでコストを抑えられることが記載されています。

### 見積もりの考え方

```
概算コスト ≒ (1 trial の学習時間) × (試行数) × (VM の時間単価)
```

- **1 trial の学習時間**はベースライン実験の `train_minutes` から分かります
- **VM の時間単価**は [Azure Machine Learning 価格](https://azure.microsoft.com/pricing/details/machine-learning/) で確認してください

> **本テキストは具体的な金額を記載しません。** 価格はリージョン・VM サイズ・時期で変わるためです。
> **必ず上記の価格ページと Microsoft Cost Management で確認してください**（[09 章](09_評価・コスト・後片付け.md) 9.4）。

## 8.6 結果を可視化する（Sweep の強み）

Azure ML studio で Sweep Job を開くと、次の 3 つのグラフが使えます。

| グラフ | 何が分かるか |
|---|---|
| **メトリック チャート** | 各 trial の学習曲線を重ねて表示 |
| **平行座標プロット** | ⭐ **どのハイパーパラメーターが主指標に効いたかが視覚的に分かる** |
| **2 次元散布図** | 2 つのパラメーターと主指標の関係 |

> **出典: Microsoft Learn** — [Visualize hyperparameter tuning jobs](https://learn.microsoft.com/azure/machine-learning/how-to-tune-hyperparameters?view=azureml-api-2#visualize-hyperparameter-tuning-jobs)

### 平行座標プロットの読み方

1. 縦軸が各パラメーターと主指標
2. 1 本の線が 1 trial
3. **主指標の高い線をたどると、どのパラメーター値を通っているかが分かる**

> ⚠ **ただし、シードを探索空間に入れている場合は注意**してください。
> **シード軸で線が大きく散らばっているなら、そのパラメーターの効果はシードのばらつきに埋もれています。**

## 8.9 学習量（`--total-timesteps`）と並列環境数（`--n-envs`）の扱い

> [!TIP]
> **深く理解するために**
>
> この 2 つは 8.1 のハイパーパラメーター表に載っていません。**性質が違うから**です。
> `--learning-rate` などは「解き方」を変えますが、**この 2 つは「どれだけ計算資源を投入するか」を変えます。**
> [06 章](06_結果の読み解き.md) 6.0.1 の診断フローで「学習量不足」「学習が遅い」に到達したときに読んでください。

### 8.9.1 `--total-timesteps`（学習量）

**ベースラインの `50000` は、[05 章](05_ベースライン実験.md) 5.2 のとおり「短時間で必ず終わる値」であって「学習を完成させる値」ではありません。**

| 判断 | 根拠にするログ | 参照 |
|---|---|---|
| **増やす価値がある** | `eval_success_rate` が**上昇傾向のまま**学習が終わっている | [06 章](06_結果の読み解き.md) 6.1「右肩上がり」 |
| **増やしても無駄な可能性が高い** | `eval_success_rate` が**完全に平坦（0 のまま）** | [06 章](06_結果の読み解き.md) 6.1。まず報酬設計・HER を疑う（[07 章](07_演習1_報酬関数の改善.md)） |
| **増やすと悪化する可能性がある** | 上がってから**落ちている** | [06 章](06_結果の読み解き.md) 6.1。先に学習率を下げる（8.1） |

> [!WARNING]
> **`--total-timesteps` はコストに直結します。**
> 8.5 の見積り式（`概算コスト ≒ 1 trial の学習時間 × 試行数 × VM の時間単価`）の「学習時間」がそのまま伸びます。
> **Sweep で `--total-timesteps` を増やすときは、`max_total_trials` を必ず見直してください。**

> [!NOTE]
> **`--total-timesteps` を変えた Run 同士は「同じ指標で比較できる」が「同じ条件ではない」点に注意してください。**
> `final_success_rate` の定義は変わらないので比較自体は成立しますが、**「学習量が違う」という差は明示的に記録**してください（[06 章](06_結果の読み解き.md) 6.6 の作法）。

### 8.9.2 `--n-envs`（並列環境数）

`--n-envs` は、**同時に動かす環境インスタンスの数**です。CPU コアを使い切れていないときに実時間を短縮できます。

| 確認するもの | 見方 |
|---|---|
| studio ［監視］の **CPU 使用率** | 低いまま＝コアが遊んでいる。`--n-envs` を増やす余地がある |
| `train_minutes` | 増やした前後で比較する |

> [!CAUTION]
> **`--n-envs` を変えた Run を、ベースラインと横並びで比較してはいけません。**
> [05 章](05_ベースライン実験.md) の TS #7 にも「**結果の比較可能性のためベースラインは変えない**」とあります。
>
> 並列数を変えると、同じ `--total-timesteps` でも**経験の集め方と更新のタイミングが変わる**ため、**「速くなっただけ」なのか「学習の質が変わった」のかを切り分けられません。**
>
> **`--n-envs` は「実時間を短縮したいとき」に使い、その Run は別条件として記録してください。**

### 8.9.3 迷ったときの優先順位

> [!IMPORTANT]
> **計算資源を増やす前に、まず「そもそも学習信号があるか」を確認してください。**
>
> 1. **`eval_video.mp4` を見る**（[06 章](06_結果の読み解き.md) 6.3）
> 2. **`eval_success_rate` が平坦でないか**を見る（[06 章](06_結果の読み解き.md) 6.1）
> 3. 平坦なら → **報酬設計・HER**（[07 章](07_演習1_報酬関数の改善.md)）。ここで `--total-timesteps` を増やしても、**コストが増えるだけで結果は変わらない可能性が高い**
> 4. 上昇傾向なら → **`--total-timesteps` を増やす**（8.9.1）
> 5. 実時間が問題なら → **`--n-envs`**（8.9.2、別条件として記録）

## ⚠ うまくいかないときは（Step 08）

| # | 症状 | 主な原因 | 確認手順 | 対処 |
|---|---|---|---|---|
| 1 | **Sweep の全 trial が即座に失敗** | **`primary_metric` 名の不一致（最頻出）** | 子ジョブのログ、記録済みメトリック名 | **`final_success_rate` と完全一致**しているか確認（[05 章](05_ベースライン実験.md) 5.3） |
| 2 | 全 trial が失敗し `ModuleNotFoundError` | `code=` / 環境の指定ミス | 子ジョブの `user_logs/std_log.txt` | 単発の Command Job で先に動作確認してから Sweep にする |
| 3 | trial が `Queued` のまま進まない | **`max_concurrent_trials` > クラスターの `max_instances`** | クラスター設定、クォータ | `max_concurrent_trials` を下げる。[02 章](02_Azure環境の準備.md) 2.3 |
| 4 | 良さそうな trial が途中で切られる | **早期終了ポリシー**（8.4） | Sweep の設定 | `delay_evaluation` を大きくする。または早期終了を使わない |
| 5 | 平行座標プロットが表示されない | メトリックが記録されていない／trial 数が少ない | 子ジョブの［メトリック］ | `final_success_rate` が記録されているか確認 |
| 6 | どのパラメーターが効いたか読めない | **シードのばらつきに埋もれている** | シード軸の散らばり | 8.3 の比較を行う。試行回数を増やす |
| 7 | Sweep が想定外に高額になりそう | 上限を設定していない | `max_total_trials` | **必ず `max_total_trials` と `timeout` を設定する**（8.5） |
| 8 | `bayesian` を指定したら怒られる | 対応していない分布を使った | 探索空間の定義 | `bayesian` は `choice` / `uniform` / `quniform` のみ対応 |
| 9 | `--seed` が trial ごとに変わっていない | 探索空間に入れ忘れ | 子ジョブの `seed` パラメーター | `job(seed=Choice(values=[...]))` の形で渡す |
| 10 | 学習率を上げたら `nan` になった | 発散 | 学習曲線 | 探索範囲の上限を下げる |
| 11 | **`--total-timesteps` を増やしても成功率が 0 のまま** | **学習信号がそもそも無い**（疎な報酬の壁） | `eval_success_rate` が平坦か | 先に報酬設計・HER を見直す（8.9.3）。**計算資源を増やす前に 06 章 6.0.1 の診断フローを辿る** |
| 12 | `--n-envs` を増やしたら成功率が変わった | **並列数を変えると経験の集め方と更新のタイミングが変わる** | MLflow の `n_envs` | **ベースラインと並べて比較しない**。別条件として記録する（8.9.2） |
| 13 | Sweep のコストが見積もりを大きく超えた | **`--total-timesteps` を増やしたまま trial 数を減らしていない** | 8.5 の見積り式 | `max_total_trials` を見直す（8.9.1） |
